# 中文 README 改版设计

## 目标

将当前英文简版 README 重写为面向项目使用者与开发者的中文综合文档。文档既要解释项目为什么存在、解决什么问题和有哪些创新，也要提供与当前代码一致的架构、协议、配置、运行和测试说明。

## 读者

- 希望了解项目设计思路的 CTF 与多 Agent 研究者。
- 准备配置 Codex、Claude Code、Kimi 等 CLI 的使用者。
- 希望阅读源码、扩展 provider 或修改调度策略的开发者。

## 项目来源与归因

README 必须明确说明：

- 项目的核心协作思想学习自 [oritera/Cairn](https://github.com/oritera/Cairn)。
- 学习内容包括从 `Origin` 到 `Goal` 的未知状态空间搜索、黑板架构，以及 `Fact / Intent / Hint` 图式协作。
- 相关学习和实践经过与 Cairn 作者沟通并获得允许。
- 本项目没有复制 Cairn 源码，不是 Cairn 的分支、兼容实现或官方项目。
- 本项目独立采用 Python 单机调度、SQLite 图黑板、按轮并发 CLI Agent、结构化 stdout 协议和人类 Hint 交互。
- 不把作者允许扩大解释为许可证豁免、商业授权或官方背书。

README 将加入 Cairn 与本项目的差异表，区分思想来源与独立实现。

## 信息结构

README 依次包含：

1. 项目名称与一句话定位。
2. 项目简介与要解决的问题。
3. 项目来源与致谢。
4. 核心设计理念。
5. `Goal / Origin / Fact / Intent / Hint` 概念说明。
6. Mermaid 系统架构图。
7. 目录结构与模块职责。
8. 图黑板、来源记录和关系类型。
9. SQLite 持久化设计与选型理由。
10. 多轮运行流程。
11. Fact 去重、冲突和最终答案共识。
12. 项目创新点。
13. 环境要求、provider 配置和命令示例。
14. `BLACKBOARD_UPDATE` 协议示例。
15. 运行产物与检查方式。
16. 测试与可靠性。
17. 适用场景、安全声明、当前限制和未来方向。

## 内容边界

- 只把当前代码已经实现的能力写成现有功能。
- Server、Web UI、Docker Worker、向量检索、远程任务队列和专用图数据库只能放在未来方向，不得描述为已实现。
- provider `priority` 只解释为展示或配置属性，不得描述为事实可信度或答案权重。
- 明确相同 Fact 使用规范化指纹合并，相似 Fact 只建立 `similar_to`，不会自动硬合并。
- 明确多 provider 环境需要两个独立 Agent 给出相同答案；仅一个 Agent 实际可用时允许单 Agent 完成。
- 测试数量写为当前已验证的 40 项，并注明测试使用本地 fake CLI，不消耗模型额度。

## 表达风格

- 中文为主，类名、文件名、协议字段和命令保持英文。
- 面向工程实践，避免营销式夸张和无法验证的性能结论。
- 先讲问题与设计，再讲使用方法；章节允许较详细，但避免重复同一概念。
- 使用 Mermaid 展示架构和轮次数据流，使用表格展示概念、模块、数据库表与 Cairn 差异。

## 验证

完成后执行：

- 搜索 README 中是否残留旧 `--prompt`、`worker.runner` 或 `RunSummary`。
- 对照 `main.py`、`orchestrator/`、`worker/providers.json` 核对命令、模块和协议字段。
- 检查 Markdown 代码块和 Mermaid 围栏是否成对闭合。
- 运行完整单元测试，确保纯文档改动没有伴随其他回归。
